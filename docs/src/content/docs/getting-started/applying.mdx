Two binaries do all the work.

- **`golemctl`** runs on your laptop. Reads your Nickel inventory, computes
  what each host should look like, signs it, ships it.
- **`golemd`** runs on each box. Receives signed bundles, verifies them
  against a public key in `/etc/golem/trusted-keys`, reconciles the box.

You apply with one command:

```bash
golemctl apply config.ncl operator.sk host-addrs.json
```

## What `golemctl apply` does

For each host in the inventory, in this order:

1. **Reads the agent's status.**
   `GET /status` returns the host's last-applied version. The next
   bundle's version is `max(last_applied) + 1` across the full apply set —
   every host in this apply gets the same fresh number, so there's no
   drift if you apply to a fleet.

2. **Compiles the Nickel for that host.**
   Walks the inventory, resolves `g.ref.host`, `g.ref.service`, and
   `g.ref.secret` placeholders, computes the firewall surface from
   `allow_from`, materializes DNS records from Ingress entries with `dns =
   true`, and produces a per-host bundle of low-level claims (write this
   file, install that package, enable this unit, add this nft fragment,
   create this DNS A record). The compilation is deterministic — the
   same input produces byte-identical output.

3. **Signs it.**
   With the operator's ed25519 secret key (`operator.sk`). The signature
   covers a canonical-form serialization of the bundle, so re-signing the
   same input gives the same signature.

4. **Posts it.**
   `POST /bundle` to the host's agent. The agent verifies the signature
   against `/etc/golem/trusted-keys`, checks monotonicity, and accepts.

If any host is unreachable during step 1, `apply` stops with a clear
error. Push without knowing every target's last-applied version risks a
partial deploy where some accept and some reject. Use `--force` to skip
an unreachable host; that host picks up at the next apply.

## What the agent does on the next tick

Once a bundle is accepted, the agent reconciles on its periodic tick
(every 30s by default). For each claim in the bundle:

- **If it's new**, the agent first reads what's already on the box (the
  current file contents, whether the package is installed, whether the
  nft fragment exists, whether the DNS record exists). It records that
  prior state in a local SQLite journal at `/var/lib/golem/state.db`.
- **Then it mutates.** Writes the file, runs `apt-get install`, runs
  `systemctl enable --now`, runs `nft -f` on the new fragment, calls the
  DNS provider's API. Whatever the claim says.

For each claim that *was* in the previous bundle but isn't anymore, the
agent does the reverse: reads the journal for the prior state, restores
it (removes the file, runs `apt-get autoremove`, removes the nft
fragment, deletes the DNS record). If a package was installed *before*
golem touched the box, removal is a no-op — golem only undoes what
golem did.

This is the property that makes apply safe: removing a service from your
inventory and re-applying restores the box to the state it was in before
you added that service. No stale files, no leaked services, no orphan
DNS records, no leftover firewall rules. See
[Honest convergence](/reference/honest-convergence/) for the full
crash-recovery story.

## Quick-reference: what the operator can see

- **Status of one host:**
  ```bash
  curl -s http://10.42.0.1:7474/status | jq
  # → { "bundle_version": 7, "node": "edge-01", "claim_count": 18 }
  ```
- **What's in the journal right now:**
  ```bash
  ssh edge-01 'sudo sqlite3 /var/lib/golem/state.db \
      "SELECT id_kind, id_key FROM claim_state;"'
  ```
- **The agent's logs:**
  ```bash
  ssh edge-01 'journalctl -u golemd -f'
  ```

## What rolling forward looks like

Edit your Nickel. Re-run `apply`. The agents pick up the new bundles on
their next tick. Image bumps, config changes, new services, new firewall
rules, new DNS records — all the same command.

```bash
# Pull a new image tag for one service
sed -i 's|lila:v123|lila:v124|' config.ncl
golemctl apply config.ncl operator.sk host-addrs.json
```

There's no rollback flag. To undo, edit your Nickel back to the previous
state and apply — same shape, version bumps forward.
