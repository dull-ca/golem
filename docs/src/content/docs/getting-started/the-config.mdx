Golem ships a toolkit of small Nickel primitives — like Ansible modules
in shape and spirit. You compose them into whatever higher-level
abstractions fit your fleet. The Nickel evaluates to a per-host bundle
that the agent applies.

```nickel
let g = import "../../nickel/lib.ncl" in

let inventory = {
  hosts = {
    "box-01" = {
      vrack_ip = "10.42.0.1",
      fragments = [
        g.package { name = "podman" },
        g.container { name = "hello", image = "ghcr.io/example/hello:v1" },
        g.firewall { name = "hello", port = 8080, allow = ["10.42.0.1"] },
      ],
    },
  },
} in

{ bundle_for = g.bundle_for inventory }
```

That's the whole shape. A host is a record. Its `fragments` array lists
what runs on that host — each fragment built from primitives.

## The primitives

These are the Ansible-module equivalents. Each takes a config record
and returns a `Fragment` (resources + handlers).

| Function | What it ensures |
| --- | --- |
| `g.file { path, content, mode?, owner?, group? }` | A file exists with given content. |
| `g.package { name, version?, hold? }` | An apt package is installed. |
| `g.unit { name, enable?, active? }` | A systemd unit is enabled and/or started. |
| `g.container { name, image, env?, volume?, command?, ... }` | A Podman Quadlet container runs. Expands into a `.container` file + a `.service` unit + a handler that restarts on change. |
| `g.firewall { name, port, allow, protocol? }` | An nftables fragment in `/etc/nftables.d/` accepting traffic to a port from listed sources. |
| `g.dns_record { zone, name, type, value, ttl? }` | A DNS record (M3 — agent provider not yet implemented). |
| `g.site { host, upstream, tls?, rate_limit?, routes?, ... }` | An nginx site block in `/etc/nginx/sites-enabled/`. |

That's the whole API surface for resources. Everything else — workload
templates, web services, databases — is *composition* of these.

## Composition

Three functions glue primitives together:

```nickel
g.combine    : Array Fragment -> Fragment            # concatenate
g.own        : String -> Fragment -> Fragment        # tag ownership
g.bundle_for : Inventory -> String -> Bundle         # per-host bundle
```

`combine` flattens fragments. `own` tags them with a refcount key — when
the last owner drops, the agent cleans the resources up. `bundle_for`
walks the inventory, resolves cross-host references, and returns the
bundle a single host should apply.

## Cross-host references

Workloads talk to other workloads by name, not address. Use the `ref`
helpers:

```nickel
env = {
  LILA_DB  = "mongodb://%{g.ref.service "mongo"}/lichess",
  REDIS    = "%{g.ref.service "redis"}",
  PG_PASS  = g.ref.secret "pg_pass",
}
```

`g.bundle_for` resolves `{mongo.service}` to the right `host:port` by
walking the inventory. Misspell a service name and the resolver leaves
the placeholder in the output — easy to spot in the bundle JSON, easy
to test before shipping. Hosts declare which service names they own:

```nickel
"db-01" = {
  vrack_ip = "10.42.0.3",
  fragments = [ ... ],
  services = [
    { name = "mongo", port = 27017 },
    { name = "redis", port = 6379  },
  ],
}
```

The `services` declaration is just a name→port map for the resolver.
The actual containers and firewall rules come from the fragments.

## Shipped abstractions (`g.contrib`)

Golem ships some pre-built compositions in `g.contrib`. They're small —
look at `nickel/contrib.ncl` to see exactly how they're built. Use them
as-is, or use them as a recipe for your own.

```nickel
g.contrib.workload    { name, image, env?, volume?, ... }
g.contrib.web_service { name, image, port, allow, env?, volume?, ... }
g.contrib.worker      { name, image, env?, ... }
g.contrib.oneshot     { name, image, env?, ... }
g.contrib.ingress     { host, upstream, dns?, dns_ip?, rate_limit?, ... }
g.contrib.postgres    { name, db, user, password, allow, version?, ... }
g.contrib.redis       { name, allow, image?, volume_size? }
g.contrib.mongo       { name, allow, image?, volume_size? }
```

`web_service` is `workload` + `firewall`. `postgres` is `web_service`
with the right image, port, volume path, and env. None of this is
magic — read the source, copy what fits, change what doesn't.

## Building your own

The point is *not* to use `g.contrib`. The point is to write
abstractions for your domain. A typical project's Nickel might look
like:

```nickel
let g = import "../../nickel/lib.ncl" in

# Your domain — a Litour service is a Django container, common env,
# always wants a postgres + redis nearby.
let litour_service = fun config =>
  g.contrib.web_service (config & {
    image = "ghcr.io/lichess4545/litour-%{config.name}:latest",
    env   = litour_env & (config.env),
  })
in

let litour_worker = fun config =>
  g.contrib.worker (config & {
    image = "ghcr.io/lichess4545/litour-%{config.name}:latest",
    env   = litour_env,
  })
in
```

Now `litour_service` and `litour_worker` are your project's vocabulary.
You compose them into your inventory like any other fragment.

## A realistic example

```nickel
let g = import "../../nickel/lib.ncl" in

let edge_ip = "10.42.0.1" in
let app_ip  = "10.42.0.2" in
let db_ip   = "10.42.0.3" in

let lila_env = {
  LILA_DB_URI = "mongodb://%{g.ref.service "mongo"}/lichess",
  LILA_REDIS  = "%{g.ref.service "redis"}",
  JAVA_OPTS   = "-Xmx12g",
} in

let inventory = {
  hosts = {
    "edge-01" = {
      vrack_ip = edge_ip,
      fragments = [
        g.contrib.ingress {
          host     = "lichess.example.com",
          upstream = "%{g.ref.service "lila"}",
          dns      = true, dns_ip = "203.0.113.10",
        },
      ],
    },

    "app-01" = {
      vrack_ip = app_ip,
      fragments = [
        g.contrib.web_service {
          name = "lila", image = "ghcr.io/lichess-org/lila:latest",
          port = 9663, allow = [edge_ip], env = lila_env,
        },
        g.contrib.worker {
          name = "fishnet", image = "ghcr.io/lichess-org/fishnet:latest",
          env = { FISHNET_KEY = g.ref.secret "fishnet_key" },
        },
      ],
      services = [{ name = "lila", port = 9663 }],
    },

    "db-01" = {
      vrack_ip = db_ip,
      fragments = [
        g.contrib.mongo { name = "mongo", allow = [app_ip] },
        g.contrib.redis { name = "redis", allow = [app_ip] },
      ],
      services = [
        { name = "mongo", port = 27017 },
        { name = "redis", port = 6379  },
      ],
    },
  },
} in

{ bundle_for = g.bundle_for inventory }
```

Three hosts, ~30 lines, covers ingress + web service + worker + mongo
+ redis with cross-host references and firewalls.

## What's *not* in the config

- **No version field.** Bundle versions are golem's bookkeeping;
  `golemctl apply` queries each host's last-applied version and bumps
  automatically.
- **No `kind:`, no `spec:`, no claim DAG.** That's the wire format the
  agent receives — your Nickel produces it, but you write at the
  primitive level (or higher).
- **No port mappings.** Cross-workload traffic uses `g.ref.service`,
  which resolves to the right host:port at translation time.
- **No `Mongo` / `Database` / `Fishnet` types in the schema.** Those
  live in `g.contrib` — and even there, they're just compositions of
  the primitives. You can replace any of them.
