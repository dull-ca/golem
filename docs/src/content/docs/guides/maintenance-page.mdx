Sometimes you want to put up a static "down for maintenance" page in
front of a domain — when you're migrating a database, doing a major
upgrade, or just need everything to stop while you investigate
something. This guide walks through writing that as a small Nickel
function, using only the **lowest-level primitives**: `g.package`,
`g.unit`, `g.file`. No `g.contrib`. No `g.container`.

The point isn't the maintenance page. The point is the *shape*:
**a parameterized template function is the API surface you build for
your fleet.** Once you have `site_down_page { host, date, reason, id }`,
flipping a domain to maintenance is one line of Nickel.

## The template

```nickel
let g = import "../../nickel/lib.ncl" in

let site_down_page = fun config =>
  let html_path = "/var/www/maintenance/%{config.id}/index.html" in
  let site_path = "/etc/nginx/sites-enabled/%{config.host}.conf" in

  let html_content = m%"
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title>%{config.host} — down for maintenance</title>
  <style>
    body { font-family: system-ui, sans-serif; max-width: 600px;
           margin: 4rem auto; padding: 2rem; text-align: center; }
  </style>
</head>
<body>
  <h1>We'll be back soon</h1>
  <p><strong>%{config.host}</strong> is temporarily unavailable.</p>
  <p>%{config.reason}</p>
  <p>Expected back: <strong>%{config.date}</strong></p>
</body>
</html>
"% in

  let site_content = m%"
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name %{config.host};

    ssl_certificate     /etc/letsencrypt/live/%{config.host}/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/%{config.host}/privkey.pem;

    root  /var/www/maintenance/%{config.id};
    index index.html;

    location / {
        return 503;
    }
    error_page 503 /index.html;
    location = /index.html { internal; }
}

server {
    listen 80;
    listen [::]:80;
    server_name %{config.host};
    return 301 https://%{config.host}$request_uri;
}
"% in

  g.own "site-down/%{config.id}" (
    g.combine [
      g.package { name = "nginx" },
      g.unit    { name = "nginx.service" },
      g.file    { path = html_path, content = html_content },
      g.file    { path = site_path, content = site_content },
    ]
  )
in
```

That's the whole template — about 35 lines of Nickel. Let's go through
the moving pieces.

## Four primitives, composed

```nickel
g.combine [
  g.package { name = "nginx" },                    # apt install nginx
  g.unit    { name = "nginx.service" },            # systemctl enable --now nginx
  g.file    { path = html_path, ... },             # write the HTML page
  g.file    { path = site_path, ... },             # write the nginx site config
]
```

`g.combine` concatenates fragments. Each primitive returns a `Fragment`
(resources + handlers); `combine` flattens them into one. That's the
whole composition story for this example.

The two `g.file` calls — one for the HTML, one for the nginx config —
are the heart of the pattern. **An nginx site config is just a file.**
You don't need a `g.site` helper to write one; you can produce the
content with Nickel's string interpolation and drop it where nginx
expects it.

## The `id` parameter

```nickel
g.own "site-down/%{config.id}" (
  g.combine [ ... ]
)
```

`g.own` tags every resource in the fragment with an owner string — a
refcount key. When you later remove this fragment from your config and
re-apply, the agent cleans up exactly the resources tagged with this
owner. **`id` is the stable name for one specific maintenance event.**

It also flows through the file paths:

```
/var/www/maintenance/temp-litour-down-2022/index.html
                     ^^^^^^^^^^^^^^^^^^^^^
                     config.id
```

This matters for a real fleet:

- **Two maintenance pages can coexist.** If `lichess.example.com` is
  down for one reason and `staging.lichess.example.com` is down for
  another, give them different `id`s and nothing collides.
- **Reverting is exact.** Remove the `site_down_page { id = "..." }`
  call from your inventory, re-apply, and only that maintenance page's
  HTML, its site config, and its owner reference vanish. The agent
  removes nginx itself only when the *last* owner of `nginx` drops.
- **You can grep for it.** `grep -r 'site-down/temp-litour-down-2022'`
  in your repo finds every spot that references this maintenance.

## Templating the content

```nickel
let html_content = m%"
  <h1>We'll be back soon</h1>
  <p><strong>%{config.host}</strong> is temporarily unavailable.</p>
  <p>%{config.reason}</p>
  <p>Expected back: <strong>%{config.date}</strong></p>
"%
```

`m%"..."%` is Nickel's multiline string. `%{expr}` interpolates. That's
all the templating you need — no Jinja, no Mustache, no Helm charts.
The same mechanism produces the nginx site config below it.

## Using it

Once `site_down_page` is defined, putting a domain into maintenance
mode is one entry in your inventory's `fragments`:

```nickel
"edge-01" = {
  public_ip = "203.0.113.10",
  vrack_ip  = "10.42.0.1",
  fragments = [
    site_down_page {
      host   = "lichess.example.com",
      date   = "May 22nd, 2026",
      reason = "Cleaning out the cobwebs",
      id     = "temp-litour-down-2022",
    },
  ],
}
```

Apply, and the agent ensures:

| Resource | What |
| --- | --- |
| `apt_package: nginx` | nginx installed (no-op if it already is). |
| `systemd_unit: nginx.service` | nginx enabled and running. |
| `file: /var/www/maintenance/temp-litour-down-2022/index.html` | the HTML page with `host`, `date`, `reason` substituted. |
| `file: /etc/nginx/sites-enabled/lichess.example.com.conf` | the nginx site block returning 503 with the page as body. |

All four resources tagged `owners: ["site-down/temp-litour-down-2022"]`.

## Taking it back down

Once maintenance is over, delete the `site_down_page { ... }` call from
your inventory and re-apply. The agent:

- Removes the nginx site config file.
- Removes the maintenance HTML.
- Removes the `nginx` package — but **only if** nothing else on the
  host still owns it. If your real `lichess.example.com` ingress is
  also using nginx, that other fragment still holds an `nginx` owner,
  so the package stays.

The journal at `/var/lib/golem/state.db` records the prior state of
each resource; if nginx was already on the box for another reason
before golem touched it (`preexisting: true`), the agent leaves it
alone. See [Honest convergence](/reference/honest-convergence/).

## Why the lowest-level primitives matter

You could write `site_down_page` using `g.contrib.ingress` instead. It
would be shorter. But the contrib version is *also* built from `g.file`,
`g.package`, and `g.unit` — go read `nickel/contrib.ncl`. The
abstraction stops being magic the moment you write your own.

The Ansible-shaped primitives (file, package, unit) are the floor.
Everything else — `g.contrib`, your own `litour_service`, your own
`site_down_page` — is just composition above that floor. Ten lines
of Nickel give you a shape your fleet didn't have before.
