The shape of every golem deploy: each host carries `fragments` built
from primitives. This guide adds a second host and a real database.
You'll see custom user-defined templates, `g.contrib` constructors,
`allow` firewall surfaces, and cross-host service references.

## The inventory

```nickel
let g = import "../../nickel/lib.ncl" in

let edge_ip = "10.42.0.1" in
let app_ip  = "10.42.0.2" in
let db_ip   = "10.42.0.3" in

# Shared env for the Django container — uses placeholders that
# golem resolves at translate time.
let app_env = {
  DATABASE_URL = "postgres://app:%{g.ref.secret "pg_password"}@%{g.ref.service "appdb"}/app",
} in

let inventory = {
  hosts = {
    # Edge: public ingress, no app code.
    "edge-01" = {
      public_ip = "203.0.113.10",
      vrack_ip  = edge_ip,
      fragments = [
        g.contrib.ingress {
          host             = "hello.example.com",
          upstream         = "%{g.ref.service "hello"}",
          dns              = true,
          dns_ip           = "203.0.113.10",
          rate_limit       = "100r/m",
          rate_limit_burst = 20,
        },
      ],
    },

    # App: the Django workload, fronted by edge-01.
    "app-01" = {
      public_ip = "203.0.113.20",
      vrack_ip  = app_ip,
      fragments = [
        g.contrib.web_service {
          name  = "hello",
          image = "ghcr.io/example/hello-django:v1",
          port  = 8000,
          allow = [edge_ip],
          env   = app_env,
        },
      ],
      services = [{ name = "hello", port = 8000 }],
    },

    # DB: postgres only, locked down to app-01.
    "db-01" = {
      vrack_ip = db_ip,
      fragments = [
        g.contrib.postgres {
          name     = "appdb",
          db       = "app",
          user     = "app",
          password = g.ref.secret "pg_password",
          allow    = [app_ip],
        },
      ],
      services = [{ name = "appdb", port = 5432 }],
    },
  },
} in

{ bundle_for = g.bundle_for inventory }
```

Three hosts, ~30 lines. Worth reading for what's there:

- **`g.contrib.web_service`** = container + firewall + podman package.
  Three primitives composed.
- **`g.contrib.postgres`** = `web_service` with the right image, port
  (5432), volume path, and env vars (`POSTGRES_USER`, `POSTGRES_DB`,
  `POSTGRES_PASSWORD`). About ten lines of Nickel — read it in
  `nickel/contrib.ncl`.
- **`g.ref.service "appdb"`** is a placeholder string. At translate
  time, `g.bundle_for` walks the inventory, finds db-01 owns the `appdb`
  service on port 5432, and substitutes `10.42.0.3:5432` everywhere the
  placeholder appeared.
- **`g.ref.secret "pg_password"`** is a placeholder for an
  operator-staged secret value. M3.
- **`allow = [app_ip]`** is the firewall rule. The translator emits an
  nftables fragment on db-01 accepting port 5432 only from `10.42.0.2`.

## What the Nickel produces

`g.bundle_for inventory "db-01"` produces a Bundle with around five
claims:

| Claim | Why |
| --- | --- |
| `apt_package: podman` | Owned by `workload/appdb` and `service/appdb`. |
| `file: /etc/containers/systemd/appdb.container` | Quadlet for the postgres container, with env vars rendered in. |
| `file: /etc/containers/systemd/appdb-data.volume` | Quadlet volume definition for the data dir. |
| `systemd_unit: appdb.service` | The generated unit, after the quadlet file. |
| `file: /etc/nftables.d/appdb-allow.nft` | nftables rule: accept 5432 from `10.42.0.2`, with a handler that reloads `nftables.service` when the file changes. |

`bundle_for "app-01"` produces similar claims for the Django container
plus its firewall fragment. `bundle_for "edge-01"` produces the nginx
package + site config + DNS record.

Every claim is a primitive [the agent already understands](/reference/architecture/).
The Nickel was just a more compact way to write it down.

## Same inventory, different deploys

The same Nickel deploys to staging by changing the addresses and
hostname:

```nickel
let edge_ip = "10.99.0.1" in
let app_ip  = "10.99.0.2" in
let db_ip   = "10.99.0.3" in

# ... and ingress.host = "staging.hello.example.com"
```

Or it deploys to a single all-in-one dev box by collapsing all the
fragments onto one host:

```nickel
"dev-01" = {
  public_ip = "127.0.0.1",
  vrack_ip  = "127.0.0.1",
  fragments = [
    g.contrib.web_service { name = "hello", image = "...", port = 8000,
                            allow = ["127.0.0.1"], env = app_env },
    g.contrib.postgres    { name = "appdb", db = "app", user = "app",
                            password = "devpass",
                            allow = ["127.0.0.1"] },
    g.contrib.ingress     { host = "hello.test", upstream = "127.0.0.1:8000" },
  ],
  services = [
    { name = "hello", port = 8000 },
    { name = "appdb", port = 5432 },
  ],
}
```

Same primitives, same shape, different topology. No special "dev mode"
in the schema — just rearranged composition.
