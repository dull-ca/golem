The shape of the input language is **describe the app, then describe the
deploy**. Two layers, both small. The app says what's running and how the
services wire to each other; the deploy says where it goes and how the world
reaches it.

## Describing the app

```nickel
let g = import "../../nickel/lib.ncl" in

app.services = {
  postgres = {
    image  = "ghcr.io/postgresql/postgresql-18:latest",
    volume = { at = "/var/lib/postgresql/data", size = "5Gb" },
    env    = {
      POSTGRES_USER     = "app",
      POSTGRES_PASSWORD = "dev-change-me",
      POSTGRES_DB       = "app",
    },
  },

  web = {
    image = "ghcr.io/example/hello-django:v1",
    env   = {
      DATABASE_URL = "postgres://app:dev-change-me@%{g.ref.service "postgres"}:5432/app",
    },
  },

  caddy = {
    image  = "caddy:2",
    config = {
      path    = "/etc/caddy/Caddyfile",
      content = m%"
        hello.example.com {
          reverse_proxy %{g.ref.port "web" 8000}
        }
      "%,
    },
  },
}
```

Three services, twelve lines. Worth reading for what's *not* there:

- **No `nodes` block.** The app doesn't know about boxes.
- **No `containers` wrapper.** A service named `postgres` is a service named
  `postgres`. The kind ("it's a container") is the default; you don't repeat
  it.
- **No `volumes` top-level.** Postgres has a volume because postgres has a
  volume. The volume's lifecycle is tied to the service that owns it.
- **No port-mapping.** Container-to-container traffic doesn't need host ports
  — the runtime gives services DNS names on a shared network. Only the
  externally-exposed service (caddy) needs a port, and that's stated in the
  deploy block, not here.

### Cross-service references

`g.ref.service "postgres"` returns the literal string `{postgres.service}`,
which is a *placeholder* the translator resolves at deploy time. It becomes
the runtime address postgres listens on (in podman's default network, just
`postgres`). The `g.ref.port "web" 8000` helper produces `{web.service}:8000`.

You can write the placeholders by hand if you prefer:

```nickel
env = { DATABASE_URL = "postgres://app:pw@{postgres.service}:5432/app" }
```

Either form is checked: misspell a service name and `golemctl` rejects the
deploy because the placeholder doesn't resolve. Strings without `{...}` pass
through untouched.

### Inline config files

The `caddy.config` field ships a config file *with* the service. The
translator mounts it into the container (or, for runtimes that can't bind-mount,
bakes it into a derived image). This keeps the rendered Caddyfile next to
the service that consumes it — no separate `volumes/caddy_config` declaration,
no `:ro` flag, no thinking about it.

## Describing the deploy

```nickel
{
  version = 1,
  app = app,                                  # the record above
  nodes = {
    "box-01" = { name = "box-01", address = "10.42.0.1" },
  },
  expose = [
    { host = "hello.example.com", service = "caddy" },
  ],
} | g.Deploy
```

That's it. One node, one public hostname. With one node defined, every service
in the app is placed there by default; you only write a `place` block when
some services go to different boxes.

## What the translator unfolds this into

Layer 2 (`golemctl`) walks `app` + `deploy` and produces ~10 layer-3 claims:

| Source | Claims produced |
| --- | --- |
| `services.postgres` | `packages.podman` + `files["/etc/containers/systemd/postgres.container"]` (rendered quadlet) + `files["/etc/containers/systemd/postgres-data.volume"]` + `units["postgres.service"]` + `units["postgres-data-volume.service"]` |
| `services.web` | `files["/etc/containers/systemd/web.container"]` + `units["web.service"]` (with `Requires=postgres.service` because of the placeholder reference) |
| `services.caddy` | `files["/etc/containers/systemd/caddy.container"]` + `files["/etc/caddy/Caddyfile"]` (the inline config) + `units["caddy.service"]` |
| `expose[0]` | adds the `hello.example.com` block to the Caddyfile + a handler that reloads caddy on Caddyfile change + ensures port 80/443 is allowed |

Every claim is a primitive [the agent already understands](/concepts/three-layers/).
The Nickel was just a more compact way to write it down.

## Same app, different deploys

The same `app` record deploys to staging by changing only the deploy block:

```nickel
{
  version = 1,
  app = app,
  nodes = { "stage-01" = { ... } },
  expose = [
    { host = "staging.hello.example.com", service = "caddy", tls = 'auto },
  ],
} | g.Deploy
```

Or to production with a beefier secret-bearing config (M3):

```nickel
{
  version = 5,
  app = app & { services.postgres.env.POSTGRES_PASSWORD = g.ref.secret "pg_password" },
  nodes = { "prod-01" = { ... } },
  expose = [
    { host = "hello.example.com", service = "caddy", tls = 'auto },
  ],
} | g.Deploy
```

The `&` is Nickel's record merge — you compose new layers on top of the app
without forking it.
