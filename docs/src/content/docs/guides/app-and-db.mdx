The shape of the input language is **describe each host, attach the
workloads that run on it, expose them as services with a firewall.**
This guide adds a second host and a real database. You'll see Workload
templates, the Workload-vs-Service split, `allow_from` rules, and
cross-host service references.

## The inventory

```nickel
let g = import "../../nickel/lib.ncl" in

# A Workload template. Plain record, no schema magic.
let web = {
  image = "ghcr.io/example/hello-django:v1",
  env   = {
    DATABASE_URL = "postgres://app:%{g.ref.secret "pg_password"}@%{g.ref.service "appdb"}/app",
  },
} in

# A postgres template — also just a record.
let postgres = fun version => {
  image  = "postgres:%{version}",
  volume = { at = "/var/lib/postgresql/data", size = "5Gb" },
} in

{
  hosts = {
    # Edge: public ingress, no app code.
    "edge-01" = {
      name      = "edge-01",
      public_ip = "203.0.113.10",
      ingress   = [
        { host = "hello.example.com", backend = "hello",
          dns = true, rate_limit = "100r/m", rate_limit_burst = 20 },
      ],
    },

    # App: the Django workload, fronted by edge-01.
    "app-01" = {
      name      = "app-01",
      public_ip = "203.0.113.20",
      vrack_ip  = "10.42.0.2",

      workloads = [ web & { name = "hello" } ],
      services  = [
        { name = "hello", workload = "hello", port = 8000,
          allow_from = ["edge-01"] },
      ],
    },

    # DB: postgres only, locked down to app-01.
    "db-01" = {
      name      = "db-01",
      vrack_ip  = "10.42.0.3",

      workloads = [
        postgres "18" & {
          name = "appdb",
          env  = {
            POSTGRES_USER     = "app",
            POSTGRES_PASSWORD = g.ref.secret "pg_password",
            POSTGRES_DB       = "app",
          },
        },
      ],

      services = [
        { name = "appdb", workload = "appdb", port = 5432,
          allow_from = ["app-01"] },
      ],
    },
  },
} | g.Inventory
```

Three hosts. Worth reading for what's there:

- **Workload = the container.** `web` and `postgres "18"` are templates
  for "thing that runs". They carry image, env, volumes — nothing about
  who can reach them.
- **Service = port + firewall.** `db-01`'s `appdb` service points at
  the `appdb` workload's port 5432 and only accepts traffic from
  `app-01`. `app-01`'s `hello` service points at the `hello` workload's
  port 8000 and only accepts traffic from `edge-01`. The translator
  emits nftables fragments on each host.
- **`dns = true` on Ingress** means golem owns the A record for
  `hello.example.com`, pointing at `edge-01.public_ip`.
- **`g.ref.service "appdb"`** resolves to db-01's address + 5432
  because db-01 owns the `appdb` service. Misspell the name and
  `golemctl apply` rejects.
- **`g.ref.secret "pg_password"`** is a placeholder for an
  operator-staged secret value. M3.

### Why two records, not one

A Workload is what podman runs. A Service is the routing surface — a
port + a firewall + a name other workloads dial. They're separate
because:

- **One workload, multiple ports.** A workload exposing both an HTTP
  port and a metrics port has two Services with different `allow_from`
  lists.
- **Pure outbound workloads have no service.** Background workers
  (celery, fishnet, queue consumers) are Workloads with zero Service
  entries — they connect out, nothing connects in.
- **Migrations.** A Workload with `oneshot = true` runs and exits.
  Nothing routes to it; no Service entry needed.

## What the translator unfolds this into

Layer 2 (`golemctl`) walks the inventory and produces three per-host
bundles totaling around 15 layer-3 claims:

| Host | Claims |
| --- | --- |
| `edge-01` | nginx site for `hello.example.com` (with rate-limit zones), nginx package + unit, nft fragment for 80/443, DNS A record `hello.example.com → 203.0.113.10` |
| `app-01` | quadlet for `hello`, systemd unit, nft fragment allowing `8000/tcp` only from edge-01's vrack address, podman package |
| `db-01` | quadlet for `appdb` postgres container, systemd unit, volume claim, nft fragment allowing `5432/tcp` only from app-01's vrack address, podman package |

Every claim is a primitive [the agent already understands](/reference/architecture/).
The Nickel was just a more compact way to write it down.

## Same inventory, different deploys

The same Nickel deploys to staging by changing host addresses and the
ingress hostname:

```nickel
"stage-edge" = {
  name      = "stage-edge",
  public_ip = "203.0.113.110",
  ingress   = [{ host = "staging.hello.example.com", backend = "hello",
                 dns = true, rate_limit = "100r/m" }],
},
```

Or it deploys to a single all-in-one box for development by collapsing
all the workload onto one host:

```nickel
"dev-01" = {
  name      = "dev-01",
  public_ip = "127.0.0.1",
  workloads = [
    web & { name = "hello" },
    postgres "18" & { name = "appdb", env = {...} },
  ],
  services  = [
    { name = "hello", workload = "hello", port = 8000,
      allow_from = ["dev-01"] },
    { name = "appdb", workload = "appdb", port = 5432,
      allow_from = ["dev-01"] },
  ],
  ingress   = [{ host = "hello.test", backend = "hello" }],
}
```

Same templates, same shape, different topology.
