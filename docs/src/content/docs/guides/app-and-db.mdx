This is the smallest deploy that's also *interesting*. One stateless web app,
one stateful database, an ingress that fronts the app on a public hostname,
and TLS via caddy.

We'll deploy [django-helloworld](https://github.com/example/django-helloworld)
(or any small Django app you have handy) on a single trixie box.

## What you write

`fleet.ncl`:

```nickel
let g = import "../../nickel/lib.ncl" in

{
  version = 1,

  nodes = {
    "box-01" = { name = "box-01", roles = ["edge", "app"], address = "10.42.0.1" },
  },

  volumes = {
    pgdata = { name = "pgdata", node = "box-01" },
  },

  containers = {
    db = {
      name  = "db",
      image = "postgres:16",
      nodes = ["box-01"],
      env   = {
        POSTGRES_USER = "app",
        POSTGRES_PASSWORD = "dev-password-change-me",
        POSTGRES_DB = "app",
      },
      volumes = [
        { source = "pgdata", destination = "/var/lib/postgresql/data" },
      ],
    },

    web = {
      name  = "web",
      image = "ghcr.io/example/django-helloworld:v1",
      nodes = ["box-01"],
      ports = [{ host = 8000, container = 8000 }],
      env   = {
        DATABASE_URL = "postgres://app:dev-password-change-me@db:5432/app",
        DJANGO_DEBUG = "false",
      },
    },
  },

  ingresses = {
    "hello.example.com" = {
      host     = "hello.example.com",
      workload = "web",
    },
  },
} | g.Fleet
```

That's the whole input. Twenty-five lines for a real deploy.

## What `golemctl` does with it

When you run:

```bash
golemctl apply fleet.ncl operator.sk node-addrs.json
```

The translator (layer 2) walks the Nickel and produces a layer-3 bundle for
`box-01`. The expansion is roughly:

| Layer 1 input | Layer 3 claims it produces |
| --- | --- |
| `containers.db` | `packages.podman` + `files["/etc/containers/systemd/db.container"]` (rendered quadlet) + `units["db.service"]` |
| `containers.web` | (`packages.podman` already declared) + `files["/etc/containers/systemd/web.container"]` + `units["web.service"]` |
| `volumes.pgdata` | `files["/etc/containers/systemd/pgdata.volume"]` + `units["pgdata-volume.service"]` (a one-shot oneshot to ensure the volume exists) |
| `ingresses["hello.example.com"]` | `packages.caddy` + `files["/etc/caddy/Caddyfile"]` (with a site block routing `hello.example.com` → `127.0.0.1:8000`) + `units["caddy.service"]` + handler: Caddyfile change → reload caddy |

So the bundle that lands on `box-01` is ~9 claims. Every one of them is a
layer-3 primitive the agent already understands. The Nickel is just a more
human shape.

## Why containers go through quadlet

Podman's quadlet mechanism turns a `.container` file in `/etc/containers/systemd/`
into a generated systemd `.service` at boot. That means:

- The agent never has to learn Podman's API. It just writes files and pokes
  systemd.
- Logs, restart policy, dependencies — all of it goes through systemd, the
  thing the agent already knows.
- Operators can `systemctl status web.service` and get the answer they expect.

This is the layered-engine principle paying off: containers are not a new
primitive at layer 3, they're a translation that produces existing primitives.

## Network between containers

In the example above, `web` connects to `db` via `postgres://...@db:5432/...`.
That works because podman puts containers in the same default network and
resolves names by container ID. For more control:

- `network: ["app-net"]` on each container puts them on a named network (golem
  emits a `.network` quadlet).
- `host` ports are explicitly mapped via `ports`.
- For container-to-container traffic without exposing on the host, just leave
  `ports` empty.

## Secrets, sort of

The example has `POSTGRES_PASSWORD = "dev-password-change-me"` in plain text.
That's fine for a dev box; for anything real:

- M2 introduces `secrets.<name>` as a layer-1 primitive.
- The operator stages secret values in `~/.golem/secrets/<name>` on the laptop.
- `golemctl apply` reads them and includes them in the signed bundle (encrypted
  to a per-node key — design TBD; we may use age for this).
- The agent writes them to a tmpfs at `/run/golem/secrets/<name>` and the
  container references them via `EnvironmentFile=/run/golem/secrets/<name>`.

For the hello-world app you wouldn't need any of that. For [Tier 3](/guides/litour/),
you do.

## What about the database itself

This guide runs postgres in a container with a named volume. That's:

- Fine for small workloads (one app, dev/staging environments, low write rate).
- Not great for production — postgres in a container has worse defaults than
  the OS package and the upgrade story is less smooth.

For real production, run postgres as an `apt_package` + a systemd unit, with
its data on a managed `files["/etc/postgresql/16/main/postgresql.conf"]` claim.
That's M1-doable today; M2 just makes the container path *also* possible.
