The shape of every golem deploy is the same: an `app` describing what runs,
plus a `deploy` saying where it goes and how the world reaches it. This guide
is that pattern at its smallest. One service. One hostname.

## The whole thing

```nickel
let g = import "../../nickel/lib.ncl" in

{
  app.services = {
    hello = { image = "ghcr.io/example/hello:v1" },
  },

  nodes  = { "box-01" = { name = "box-01", address = "10.42.0.1" } },
  expose = [{ host = "hello.example.com", service = "hello" }],
} | g.Deploy
```

That's the deploy. Three fields. No version number — `golemctl apply` reads
each node's last-applied version and bumps automatically.

- **`app.services.hello`** — one container. The image is whatever you're
  shipping. No env, no volume, no command override; defaults are fine for a
  hello-world.
- **`nodes`** — one box, addressable at `10.42.0.1`.
- **`expose`** — `hello.example.com` is fronted by golem's caddy, which
  reverse-proxies to the `hello` service.

## Apply it

<Steps>
1. From the operator's laptop:

   ```bash
   golemctl apply config.ncl operator.sk node-addrs.json
   ```

2. Wait one tick (the agent reconciles every 30s by default):

   ```bash
   curl -s http://10.42.0.1:7474/status | jq
   ```

3. Hit the hostname. With DNS pointed at the box, you get TLS-terminated
   traffic to your container:

   ```bash
   curl https://hello.example.com
   ```
</Steps>

## What golem did under the hood

The translator unfolded those five lines into roughly six layer-3 claims that
the agent then applied:

| Claim | Why |
| --- | --- |
| `apt_package: podman` | Required for any service. |
| `file: /etc/containers/systemd/hello.container` | The quadlet that defines the `hello` container. |
| `systemd_unit: hello.service` | Auto-generated from the quadlet, enabled and active. |
| `apt_package: caddy` | Required because `expose` is non-empty. |
| `file: /etc/caddy/Caddyfile.d/hello.example.com.caddy` | Site block routing the hostname to `hello.service:80`. |
| `systemd_unit: caddy.service` | Enabled and active, with a handler that reloads on Caddyfile change. |

You don't write any of that. The agent journals each claim's prior state
before mutating, so removing them later restores the box honestly. That's the
part that makes golem worth using over a shell script.

## Take it back

Edit the Nickel to empty out `app.services` and `expose`, then re-apply:

```nickel
{
  app.services = {},
  nodes  = { "box-01" = { name = "box-01", address = "10.42.0.1" } },
  expose = [],
} | g.Deploy
```

After the next tick:

- `hello.service` is stopped and disabled, the quadlet file is removed.
- `caddy.service` is stopped, the Caddyfile fragment is removed.
- Both `podman` and `caddy` are removed via `apt-get autoremove` — *only
  because* golem captured `preexisting: false` for each when it first
  installed them. If either was already on the box for another reason, the
  unapply leaves it alone.
- The journal in `/var/lib/golem/state.db` is empty.

The empty journal is the proof that nothing leaked. Honest unapply is what
makes golem safe to use on a box you also touch by hand for other reasons.
See [Journal-before-mutate](/concepts/journal/) for how this stays honest
even across crashes.
