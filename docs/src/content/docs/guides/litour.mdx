[Litour](https://codeberg.org/dull/litour) is the league management
software that runs the [Lichess 4545 League](https://www.lichess4545.com/)
and several other team chess leagues. It's a real, multi-service,
secrets-bearing, publicly-routed Django app — the workload that
motivated golem.

This guide deploys the full stack across three hosts: an edge box
terminating ingress, an app box running the Django workloads and
workers, and a data box running redis and postgres. Along the way it
shows the move users care about: **building your own domain
abstractions on top of golem's primitives**.

## Step 1 — your domain vocabulary

Litour has seven container variants — web, api, apiworker, ui, celery,
watcher, migrate. They all share an image registry, common env, and
secrets. Instead of writing each one as a raw `g.contrib.web_service`,
build a `litour_service` and `litour_worker` for your project:

```nickel
let g = import "../../nickel/lib.ncl" in

let secret = g.ref.secret in

let litour_image = fun n => "ghcr.io/lichess4545/litour-%{n}:latest" in

let litour_env = {
  DATABASE_URL      = "postgres://litour:%{secret "pg_pass"}@%{g.ref.service "appdb"}/litour",
  REDIS_URL         = "redis://%{g.ref.service "redis"}",
  SECRET_KEY        = secret "django_secret",
  LICHESS_API_TOKEN = secret "lichess_token",
  EMAIL_HOST_USER   = secret "email_user",
  EMAIL_HOST_PASS   = secret "email_pass",
} in

# A litour service: a web_service with the litour image + env baked in.
let litour_service = fun config =>
  g.contrib.web_service (config & {
    image = litour_image config.name,
    env   = litour_env & (if std.record.has_field "env" config then config.env else {}),
  })
in

# A litour worker: a background container, dial-out only, no port.
let litour_worker = fun config =>
  g.contrib.worker {
    name  = config.name,
    image = litour_image config.name,
    env   = litour_env & (if std.record.has_field "env" config then config.env else {}),
  }
in

# A litour oneshot — the migrate container, runs and exits.
let litour_oneshot = fun config =>
  g.contrib.oneshot {
    name  = config.name,
    image = litour_image config.name,
    env   = litour_env,
  }
in
```

Three functions, ~25 lines. Now your inventory speaks litour, not
"workload-with-litour-config-baked-in".

## Step 2 — the inventory

```nickel
let app_ip = "10.42.0.2" in
let db_ip  = "10.42.0.3" in

let inventory = {
  hosts = {
    # ── Edge: public-facing nginx, owns DNS for the zone. ────────────
    "edge-01" = {
      public_ip = "203.0.113.10",
      vrack_ip  = "10.42.0.1",
      fragments = [
        g.contrib.ingress {
          host             = "www.lichess4545.com",
          upstream         = "%{g.ref.service "web"}",
          dns              = true,
          dns_ip           = "203.0.113.10",
          rate_limit       = "200r/m",
          rate_limit_burst = 50,
          conn_limit       = 100,
          buffering        = false,
          routes = [
            { path = "/v2/api", backend = "api" },
            { path = "/v2",     backend = "ui"  },
          ],
        },
      ],
    },

    # ── App: every Django workload + the workers + the migrate oneshot.
    "app-01" = {
      public_ip = "203.0.113.20",
      vrack_ip  = app_ip,
      fragments = [
        litour_service { name = "web", port = 8000, allow = ["10.42.0.1"] },
        litour_service { name = "api", port = 8001, allow = ["10.42.0.1"] },
        litour_service { name = "ui",  port = 3000, allow = ["10.42.0.1"],
                         env  = { LITOUR_API_BASE_URL = "http://%{g.ref.service "api"}" } },

        # apiworker is internal — only dialable from app-01 itself.
        litour_service { name = "apiworker", port = 8002, allow = [app_ip] },

        # No port: dial out only.
        litour_worker { name = "celery"  },
        litour_worker { name = "watcher" },

        # Runs and exits.
        litour_oneshot { name = "migrate" },
      ],
      services = [
        { name = "web",       port = 8000 },
        { name = "api",       port = 8001 },
        { name = "ui",        port = 3000 },
        { name = "apiworker", port = 8002 },
      ],
    },

    # ── Data: redis + postgres. Locked down to app-01. ────────────────
    "data-01" = {
      public_ip = "203.0.113.30",
      vrack_ip  = db_ip,
      fragments = [
        g.contrib.postgres {
          name     = "appdb",
          version  = "18",
          db       = "litour",
          user     = "litour",
          password = secret "pg_pass",
          allow    = [app_ip],
          configs  = [
            { path    = "/etc/postgresql/18/main/conf.d/golem.conf",
              content = m%"
                listen_addresses = '*'
                max_connections = 200
              "%, },
          ],
        },

        g.contrib.redis {
          name  = "redis",
          allow = [app_ip],
        },
      ],
      services = [
        { name = "appdb", port = 5432 },
        { name = "redis", port = 6379 },
      ],
    },
  },
} in

{ bundle_for = g.bundle_for inventory }
```

That's the whole deploy. Three hosts, ~80 lines including the domain
vocabulary at the top. Read what's there:

- **Domain vocabulary up front.** `litour_service`, `litour_worker`,
  `litour_oneshot` — the shapes you actually deploy. Each is one
  function, three or four lines, calling a `g.contrib` constructor with
  litour-specific defaults.
- **Pure-outbound workloads use `litour_worker`.** Celery, watcher
  connect out (postgres, redis, the lichess API). Nothing connects in,
  so they don't expose a port — `litour_worker` doesn't take one.
- **Migrations use `litour_oneshot`.** Runs once and exits.
  Re-applying with a new image runs migrate again with that image.
- **Firewall is tight.** Each `litour_service`'s `allow` list controls
  who reaches it. apiworker is `[app_ip]` — only the app box itself.
  web/api/ui are `[edge_ip]` — only edge-01.
- **DNS owned by edge-01.** `dns = true` on the ingress.
- **Routes inside an ingress.** `/v2/api/*` → api, `/v2/*` → ui,
  fall-through → web. nginx `location` blocks materialized from those
  three lines.

## Operator workflow

<Steps>
1. **Stage the secrets locally:**

   ```bash
   mkdir -p ~/.golem/secrets/litour-prod
   echo 'verysecret'          > ~/.golem/secrets/litour-prod/pg_pass
   echo 'django-secret-key'   > ~/.golem/secrets/litour-prod/django_secret
   echo 'lip_xxx'             > ~/.golem/secrets/litour-prod/lichess_token
   echo 'mailgun-user'        > ~/.golem/secrets/litour-prod/email_user
   echo 'mailgun-password'    > ~/.golem/secrets/litour-prod/email_pass
   chmod -R 0600 ~/.golem/secrets
   ```

2. **Apply:**

   ```bash
   golemctl apply config.ncl operator.sk host-addrs.json
   ```

3. **Watch the rollout:**

   ```bash
   for h in edge-01 app-01 data-01; do
     ssh $h 'curl -s http://127.0.0.1:7474/status | jq'
   done
   ssh app-01 'systemctl status web.service api.service ui.service'
   ```

4. **Roll forward.** Bump an image tag (or change the `litour_image`
   helper), re-apply. The version monotonically increases; the agent
   does the right thing on each host.
</Steps>

## What you just did

You wrote three small functions — `litour_service`, `litour_worker`,
`litour_oneshot` — that became your project's vocabulary. They're built
on top of `g.contrib` constructors, which are built on top of golem's
primitives, which compile down to per-host bundles of files +
packages + units.

Nothing in golem knew the word "litour". You taught it.

That's the move: the schema doesn't predict your fleet. You predict
your fleet, and use golem's primitives to express it.

## Migrating from compose

If you already run litour via `docker compose`, the mechanical
translation:

| compose | nickel |
| --- | --- |
| `services.<name>.image` | a `g.container`'s `image` (or higher-level wrapper) |
| `services.<name>.environment` | `.env` |
| `services.<name>.command` | `.command` |
| `services.<name>.volumes: ["named:/path"]` | `.volume = { at = "/path", size = "..." }` |
| `services.<name>.ports: ["8080:8080"]` | `g.firewall { port, allow }` + a `services` registration |
| `secrets.<name>` (file:) | `g.ref.secret "<name>"` referenced in env |
| nginx site / Caddyfile | `g.contrib.ingress` on the edge host |
| `networks:` block | (gone — host network + `allow` lists) |
| `depends_on:` | (gone — placeholder references imply ordering) |
| All services in one file | Inventory across multiple hosts |

`golemctl translate compose.yml > config.ncl` will be a real command in
M2; it places everything on one host and you split it up by host as you
need to.

## What this gives you compose doesn't

- **Multi-host out of the box.** Compose is one Docker daemon. This is
  three boxes with shared firewall semantics.
- **First-class firewall.** Every workload's `allow` is the rule. No
  manual `iptables` / `ufw` / cloud security group sprawl.
- **First-class DNS.** `dns = true` on Ingress. Add a host, get a
  record; remove a host, lose the record. No separate Terraform DNS
  module to drift out of sync.
- **References, not stringly-typed addresses.** `g.ref.service "appdb"`
  is checked at translation; `data-01` in compose is a string the
  network might or might not resolve.
- **Domain vocabulary.** `litour_service` is your project's word, not
  golem's. Compose forces you to write the same Docker boilerplate
  every time.
- **Honest unapply.** Remove a workload's fragment from a host and
  re-apply; the agent stops + disables the unit, removes the quadlet,
  removes the firewall rule, removes the journal entry. No leaked
  state.

## What it doesn't give you

- **Built-in mTLS for east-west traffic.** Run on a Nebula tunnel for
  that.
- **Auto-rollback on health-check failure.** M4 may add health-gated
  rollback; for now, you SSH in and re-apply the previous config.
- **Horizontal autoscaling.** This is for fleets where the host count
  changes on the order of months, not seconds.
