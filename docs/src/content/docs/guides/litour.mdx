[Litour](https://codeberg.org/dull/litour) is the league management software
that runs the [Lichess 4545 League](https://www.lichess4545.com/) and several
other team chess leagues. It's a real, multi-service, secrets-bearing,
publicly-routed Django app — exactly the workload that motivated golem.

This guide deploys the full stack on a single trixie box. It's not a
hypothetical example — it's the deploy story for litour-prod.

## The app

Same shape as [Tier 2](/guides/app-and-db/), more services. The app definition
is a flat record of named services that wire to each other:

```nickel
let g = import "../../nickel/lib.ncl" in

let secret = g.ref.secret in              # M3 placeholder helper
let svc    = g.ref.service in

let litour_image = fun name =>            # local helper, not part of golem
  "ghcr.io/lichess4545/litour-%{name}:latest" in

let litour_env = {
  DATABASE_URL      = secret "db_url",
  SECRET_KEY        = secret "django_secret",
  LICHESS_API_TOKEN = secret "lichess_token",
  EMAIL_HOST_USER   = secret "email_user",
  EMAIL_HOST_PASS   = secret "email_pass",
} in

app.services = {
  redis = {
    image   = "redis:7-alpine",
    command = "redis-server --appendonly yes",
    volume  = { at = "/data", size = "1Gb" },
  },

  web       = { image = litour_image "web",       env = litour_env },
  api       = { image = litour_image "api",       env = litour_env },
  apiworker = { image = litour_image "api-worker", env = litour_env },
  ui        = {
    image = litour_image "ui",
    env   = { LITOUR_API_BASE_URL = "http://%{svc "api"}:8001" },
  },
  celery   = { image = litour_image "celery",  env = litour_env },
  watcher  = { image = litour_image "watcher", env = litour_env },

  migrate = {
    image   = litour_image "migrate",
    env     = litour_env,
    oneshot = true,                       # runs once, exits
  },

  caddy = {
    image  = "caddy:2",
    config = {
      path    = "/etc/caddy/Caddyfile",
      content = m%"
        www.lichess4545.com {
          handle_path /v2/api/* { reverse_proxy %{svc "api"}:8001 }
          handle_path /v2/*     { reverse_proxy %{svc "ui"}:3000 }
          handle                { reverse_proxy %{svc "web"}:8000 }
        }
      "%,
    },
  },
}
```

Nine services, fifty-ish lines of Nickel. Read it: every service is a *thing
that runs*. There's no quadlet boilerplate, no `nodes = ["box-01"]` repeated
ten times, no separate `volumes` block, no `networks` block.

The `litour_image` and `litour_env` lets are local conveniences — a litour
operator's habit, not a golem feature. They're just Nickel functions and
records.

## The deploy

Postgres is *not* in the app — for production, it runs as an apt-installed
package on the host (better defaults, smoother upgrades than the container).
That's an OS-level concern, so it lives in `system.packages`:

```nickel
{
  version = 1,
  app = app,

  nodes = {
    "box-01" = { name = "box-01", address = "10.42.0.1" },
  },

  expose = [
    { host = "www.lichess4545.com", service = "caddy", tls = 'auto },
  ],

  system.packages = { postgresql-16 = { name = "postgresql-16" } },
  system.units    = { "postgresql.service" = { name = "postgresql.service" } },
  system.files = {
    "pg-tuning" = {
      path    = "/etc/postgresql/16/main/conf.d/golem.conf",
      content = m%"
        listen_addresses = '127.0.0.1'
        max_connections = 200
      "%,
    },
  },
} | g.Deploy
```

`system` is the layer-3 escape hatch — when the App model can't (or
shouldn't) express something, you drop to raw `packages` / `files` / `units`
and the agent still treats them as honestly-unappliable claims.

## Operator workflow

<Steps>
1. **Stage the secrets locally:**

   ```bash
   mkdir -p ~/.golem/secrets/litour-prod
   echo 'postgres://litour:...@127.0.0.1/litour' > ~/.golem/secrets/litour-prod/db_url
   echo 's3cr3t' > ~/.golem/secrets/litour-prod/django_secret
   # … one file per name referenced by g.ref.secret
   chmod -R 0600 ~/.golem/secrets
   ```

2. **Apply:**

   ```bash
   golemctl apply config.ncl operator.sk node-addrs.json
   ```

3. **Watch the rollout:**

   ```bash
   ssh box-01 'curl -s http://127.0.0.1:7474/status | jq'
   ssh box-01 'systemctl status web.service api.service ui.service'
   ```

4. **Roll forward.** Bump an image tag (or the whole `litour_image` helper),
   re-apply. The version monotonically increases; the agent does the right
   thing.
</Steps>

## Migrating from compose

If you already run litour via `docker compose`, the mechanical translation:

| compose | nickel |
| --- | --- |
| `services.<name>.image` | `services.<name>.image` |
| `services.<name>.environment` | `services.<name>.env` |
| `services.<name>.command` | `services.<name>.command` |
| `services.<name>.volumes: ["named:/path"]` | `services.<name>.volume = { at = "/path" }` |
| `secrets.<name>` (file:) | `g.ref.secret "<name>"` referenced in env |
| Caddyfile in a separate config | `services.caddy.config` (inline) |
| `networks:` block | (gone — implicit shared network) |
| `depends_on:` | (gone — placeholder references imply ordering) |

`golemctl translate compose.yml > config.ncl` will be a real command in M2.

## What this gives you compose doesn't

- **One file describes the app, another describes the deploy.** Move the same
  app between dev/staging/prod by swapping the deploy block.
- **References, not stringly-typed addresses.** `{api.service}` is checked at
  translation; `api:8001` in compose is a string the network might or might
  not resolve.
- **Honest unapply.** Remove `services.celery` from the app and re-apply; the
  agent stops + disables `celery.service`, removes the quadlet file, cleans
  the systemd state. Compose has no rollback story for the OS-level `system`
  bits.
- **No control plane to keep up.** The agent runs on each box; no Swarm, no
  Portainer, no orchestrator daemon to babysit.

## What it doesn't give you

- **Built-in mTLS for east-west traffic.** Run on a Nebula tunnel for that.
- **Auto-rollback on health-check failure.** M4 may add health-gated rollback;
  for now, you SSH in and re-apply the previous config.
- **Horizontal autoscaling.** This is for fleets where the box count changes
  on the order of months, not seconds.
