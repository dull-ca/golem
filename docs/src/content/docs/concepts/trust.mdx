The agent (`golemd`) does not authenticate the network. It authenticates the
**bundle**.

## What the agent trusts

Exactly one thing: the operator's ed25519 public key (or, optionally, a small
allowlist of keys). It's stored at `/etc/golem/trusted-keys` as a flat file of
hex-encoded public keys, one per line.

Anything signed by that key is treated as authoritative. The agent will:

1. Verify the signature.
2. Check that `bundle.node` matches its own configured node name (you can't
   accidentally apply node A's bundle to node B).
3. Check that `bundle.version > last_applied_version` (rollback prevention).

If any of those fail, the bundle is rejected with HTTP 400 and the agent
continues running the previous bundle.

## What the agent doesn't trust

- **The network.** The HTTP listener defaults to `127.0.0.1:7474`. You're
  expected to run it behind a Nebula tunnel, on a Unix socket, or accessible
  only via SSH port-forward. The agent doesn't care; the cryptography is what
  makes the push safe.
- **The operator's laptop.** If the laptop is compromised and the signing key
  is stolen, the attacker can sign bundles. That's the scope of the trust.
  Treat the signing key like an SSH key.
- **The bundle's source.** Golem doesn't care if the bundle came from `curl`,
  a CI runner, an operator typing `golemctl push`, or a teammate. The signature
  is what authorizes the change.

## Two trust tiers in the input language

The two sub-layers of Layer 1 map naturally to two trust tiers:

- **Tenant-trust** — the **`app`** block. A team can declare what containers
  run, what env they need, what volumes they own, how they wire to each
  other. Nothing in `app` reaches the host directly; every service compiles
  to a quadlet + a unit.
- **Operator-trust** — the **`deploy`** block, especially `system.*`. Node
  placement, public hostnames, and any raw `packages` / `files` / `units`
  escape hatches. These touch the host; the operator's signing review is
  what authorizes them.

<Aside type="note">
  This split lives in `golemctl` — it's enforced at signing/translation time,
  not by the agent. M2 will add a "tenant-only signing key" mode where the
  operator's key co-signs over a tenant-only `app` sub-bundle, but for now
  the operator signs everything.
</Aside>

## Threat model in one paragraph

An attacker on the network can't push anything that the agent will apply. An
attacker who steals a copy of the SQLite journal learns what's installed on the
box (nothing secret). An attacker who steals the operator's signing key can do
anything — same blast radius as stealing root SSH access. An attacker who
compromises a single agent can corrupt that one node but can't propagate.

This is deliberately a small fleet's threat model. If you have 1000 nodes and
need RBAC across operator teams, you want different software.
