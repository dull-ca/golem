Golem is **three layers stacked on each other**. Most orchestrators collapse
them into one big YAML; golem keeps them separate because each one has
different change-frequency, different audience, and a different threat model.

## Layer 1 — input language

What the operator writes. Nickel, with **two sub-layers** that have different
audiences and change at different rates:

### `app` — what's running

A graph of named **services** that wire to each other:

```nickel
app.services = {
  postgres = { image = "postgres:16", volume = { at = "/var/data" } },
  web      = { image = "...", env = { PG_URL = "{postgres.service}:5432" } },
  caddy    = { image = "caddy:2", config = { ... } },
}
```

The app describes the *application* — what containers run, what data they
persist, how they reference each other. It says nothing about which box runs
it or how the public reaches it. The same `app` deploys to staging and prod
unchanged.

### `deploy` — where it goes, how it's exposed

```nickel
{
  version = 1,
  app     = app,
  nodes   = { "box-01" = { ... } },
  expose  = [{ host = "hello.example.com", service = "caddy" }],
  system  = { packages = { postgresql-16 = { ... } } },
} | g.Deploy
```

The deploy block places services on nodes, names public hostnames, and
optionally drops to raw layer-3 claims via `system` for OS-level concerns
the App model can't express (kernel sysctls, custom timers, an apt-managed
postgres on the host instead of a container).

### Cross-service references

Services refer to each other via placeholders the translator resolves:

- `{name.service}` — the runtime address of a named service
- `g.ref.service "name"` — Nickel helper that emits the same placeholder
  but is checked: misspelled service names are rejected at translate time
- `g.ref.secret "name"` — placeholder for an operator-supplied secret value
  (M3)

You never type a port mapping or a container name. Saying "the postgres
service" makes it work.

<Aside type="note">
  In M1 only the layer-3 primitives are implemented; the agent literally
  doesn't know what a "service" is yet. M2 adds the App/Deploy input language
  by translating each service into a quadlet `.container` file + a systemd
  unit — both of which *are* layer-3 primitives the agent already understands.
</Aside>

## Layer 2 — translation

`golemctl` runs on the operator's laptop. It:

1. Reads the Nickel input.
2. Validates contracts (each `Workload` has a `name`, an `image`, a non-empty
   `nodes` list, etc.).
3. Resolves all `{name.service}` and `g.ref.*` placeholders against the
   actual services in the app.
4. Translates each service into a set of layer-3 claims. A `services.api`
   becomes:
   - a `files["/etc/containers/systemd/api.container"]` claim with the
     rendered quadlet body
   - a `packages.podman` claim (transitively required by every service)
   - a `units["api.service"]` claim that depends on the file claim
5. Adds `system.*` claims verbatim from the deploy block.
6. Computes a per-node bundle (only the claims that node owns).
7. Signs it with the operator's ed25519 key.
8. Sends it to each node's `golemd` over HTTP.

The translation is **deterministic** and **canonical** — the same Nickel input
produces byte-identical bundles. That matters because the agent's monotonicity
check rejects bundles with `version <= last_applied`, and you don't want a
re-sign to break that.

## Layer 3 — system engine

The `golemd` agent. Tiny. Speaks three primitives only:

- `files["/some/path"]` — write a file with given content/mode
- `packages.<name>` — apt install / autoremove
- `units["foo.service"]` — `systemctl enable --now`, `disable`, etc.

Plus the bookkeeping every claim needs: capture prior state before mutating,
journal it, mutate, journal "applied". When a claim is removed from a future
bundle, *unapply* it using the captured prior state. When a previously-installed
package was already on the box for another reason, leave it alone.

The whole agent is ~3000 lines of Rust. It deliberately doesn't know about
services, exposes, volumes, or anything that lives at layer 1.

## Why split it this way

<table>
  <thead>
    <tr><th>Concern</th><th>Lives at</th><th>Changes</th><th>Failure mode</th></tr>
  </thead>
  <tbody>
    <tr>
      <td>What I'm running</td>
      <td>Layer 1 (Nickel)</td>
      <td>Daily</td>
      <td>Operator catches it in CI / signing review</td>
    </tr>
    <tr>
      <td>How it lands on a box</td>
      <td>Layer 2 (`golemctl`)</td>
      <td>Per release</td>
      <td>Bundle rejected at signing or by agent</td>
    </tr>
    <tr>
      <td>What's actually on the box</td>
      <td>Layer 3 (`golemd`)</td>
      <td>Almost never</td>
      <td>Crash → recover honestly on next tick</td>
    </tr>
  </tbody>
</table>

The layer-3 engine is the part that can corrupt your boxes. So it's the part we
test the hardest — every journal-before-mutate window has a `GOLEM_CRASH_AFTER`
injection point and a smoke test that aborts the agent there.

## What the docs assume

Most pages talk in layer-1 terms — that's what an operator writes. When a guide
says "this becomes a quadlet file plus a systemd unit," that's the layer-2
translation; you won't write those by hand unless you want to.

The [Bundle format](/reference/bundle-format/) reference is the layer-3 wire
format if you ever need to inspect a signed bundle directly.
